## Phase Boundary

The self-improvement loop, built while Phase 6 collects data: per-strategy P&L dashboards (simple HTML/markdown is fine), tournament rules encoded (30-trade minimum, Sharpe-based judging, probation sizing), the new-strategy pipeline (backtest → out-of-sample → paper 30 trades → probation at 25% size → full), and a cap of 5–6 active strategies with limited mutations per quarter. <decisions>
## Implementation Decisions

Auto-selected defaults under the owner's standing full-auto directive. Override any before planning.

### Attribution Dashboards
- **D-01:** A static report generator (markdown + a single self-contained HTML file, no server, no JS frameworks) reading `paper_trades`/`backtest_runs`: per-strategy equity curves, PF/Sharpe/max-DD/win-rate tables, per-symbol breakdowns, kill-condition proximity gauges. Regenerated by a scheduled task alongside the daily report.
- **D-02:** Attribution reads ONLY the ledgers (paper_trades for live-paper, backtest_trades for historical) — no parallel bookkeeping.

### Tournament Rules (pre-registered)
- **D-03:** Eligibility: a strategy enters judging only after ≥30 closed paper trades (phase doc). Judging metric: annualised Sharpe on closed-trade returns, tie-broken by profit factor. Evaluation cadence: weekly, on a schedule, writing an auditable decision record.
- **D-04:** States and transitions: `probation` (25% size) → `full` after 30 trades with Sharpe above the pre-registered floor; `full` → `retired` on kill-condition trip (immediate, no appeal — standing rule) or on sustained bottom-rank per pre-registered demotion rule; `retired` is terminal for that config (a changed config is a NEW entrant).
- **D-05:** Cap: at most 6 active (probation+full) strategies; at most 2 new entrants per quarter (the phase doc's "limited mutations"). Entrants queue beyond the cap.
- **D-06:** All thresholds (Sharpe floor, demotion rule, cap numbers) live in a frozen config committed BEFORE the first real tournament run — standing rule 1 applied to the tournament itself.

### New-Strategy Pipeline
- **D-07:** Encoded as a checklist state machine per entrant: backtest-passed (Phase 2/3 machinery evidence required: run_ids) → OOS-passed (oos_results reference) → paper-30 (ledger count) → probation → full. No stage skippable in code; each transition stamps its evidence.

### Integration & Ops
- **D-08:** Tournament decisions WRITE the same live-config store Phase 5 reads (`trader/paper/config.py`'s registry becomes DB-backed or file-regenerated in a controlled way the planner determines), so promote/retire takes effect at the next entry-pipeline run without code edits. Retire also triggers the existing kill/retire path.
- **D-09:** Every tournament run appends a full audit record (inputs, metrics, decisions, config hash) and sends a Telegram summary. Owner audit is the phase's exit check — decisions must be traceable to numbers.
- **D-10:** Scheduled via the same Task Scheduler pattern (weekly), registration deferred to the existing 05-09 go-live checkpoint batch (one more schtasks line — no separate human session).

### Claude's Discretion
