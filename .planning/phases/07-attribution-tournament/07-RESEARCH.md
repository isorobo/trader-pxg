# Phase 7: Attribution & Tournament - Research

**Researched:** 2026-07-28
**Domain:** Tournament state machine + report generation over an existing SQLite paper-trading ledger (no new services, no new external packages)
**Confidence:** HIGH for integration surface (verified by reading the actual call sites), MEDIUM for the exact demotion-formula defaults (pre-registered numbers are a judgment call the owner should confirm), HIGH for "no new deps" (verified against the actual venv)

## Summary

Phase 7 adds one new SQLite migration (`0006_tournament.sql`) and one new package
(`trader/tournament/`) on top of an already-working Phase 5 paper-trading loop.
The single hardest integration point is D-08: `trader/paper/config.py`'s
`LIVE_STRATEGY_CONFIGS` tuple is read from exactly four places
(`guardian.evaluate_kill_conditions`, `entry_pipeline._live_profile_names`,
`entry_pipeline.run_entry_pipeline_once`'s two `LIVE_STRATEGY_CONFIGS_BY_PROFILE_NAME`
lookups, and `daily_report.compute_paper_section`). All four already take a `conn`
argument, so swapping the hardcoded tuple for a DB-backed loader is a genuinely
minimal, mechanical diff — provided the loader lives in a *new* module, not inside
`config.py` itself, because `config.py`'s own docstring is an explicit "no I/O"
contract that a DB read would violate.

The rest of the phase reuses existing, already-tested machinery almost entirely:
`trader/backtest/metrics.py`'s `compute_metrics`/`sharpe_ratio`/`profit_factor`
for all judging math (no new statistics code needed), the
`breakers.py`/`reconcile.py` append-only-log-plus-derived-state convention for the
tournament's own state, and the `frozen_config_v2.py` sha256 hash-gate pattern for
D-06's frozen tournament thresholds. The venv has **no matplotlib** (only numpy,
pandas, pandas_market_calendars) — dashboards must render equity curves as
hand-built inline SVG polylines, not a plotting library. No new pip packages are
required anywhere in this phase.

**Primary recommendation:** Build `trader/tournament/` as a thin decision layer
over the existing ledger — one new migration, one new frozen-config module (byte-
hash gated like `frozen_config_v2.py`), one new DB-backed config loader consumed
by the four existing Phase 5 call sites, and a static-report generator built on
`metrics.compute_metrics` + hand-rolled SVG. Do not reimplement Sharpe/PF, do not
invent a new state-persistence pattern, and do not put DB I/O inside
`trader/paper/config.py`.

### Locked Decisions

- **D-01:** A static report generator (markdown + a single self-contained HTML file, no server, no JS frameworks) reading `paper_trades`/`backtest_runs`: per-strategy equity curves, PF/Sharpe/max-DD/win-rate tables, per-symbol breakdowns, kill-condition proximity gauges. - **D-05:** Cap: at most 6 active (probation+full) strategies; at most 2 new entrants per quarter (the phase doc's "limited mutations"). Entrants queue beyond the cap.
- **D-06:** All thresholds (Sharpe floor, demotion rule, cap numbers) live in a frozen config committed BEFORE the first real tournament run — standing rule 1 applied to the tournament itself.
- **D-07:** Encoded as a checklist state machine per entrant: backtest-passed (Phase 2/3 machinery evidence required: run_ids) → OOS-passed (oos_results reference) → paper-30 (ledger count) → probation → full. No stage skippable in code; each transition stamps its evidence.

- **D-09:** Every tournament run appends a full audit record (inputs, metrics, decisions, config hash) and sends a Telegram summary. Owner audit is the phase's exit check — decisions must be traceable to numbers.
- **D-10:** Scheduled via the same Task Scheduler pattern (weekly), registration deferred to the existing 05-09 go-live checkpoint batch (one more schtasks line — no separate human session).

## Q1: The Config-Store Transition (D-08) — the hardest integration point

**Confidence: HIGH** — every claim below is `[VERIFIED: codebase]` by direct read of `trader/paper/config.py`, `ledger.py`, `guardian.py`, `entry_pipeline.py`, `daily_report.py`, and `migrations/0005_paper_trading.sql`.

### Every call site of `LIVE_STRATEGY_CONFIGS` / `LIVE_STRATEGY_CONFIGS_BY_PROFILE_NAME` today

| File | Function | Usage |
|------|----------|-------|
| `trader/paper/guardian.py` | `evaluate_kill_conditions(conn)` | `for cfg in config.LIVE_STRATEGY_CONFIGS:` — reads `strategy_id`, `pf_floor`, `max_dd_kill`, `consecutive_loss_kill` |
| `trader/paper/entry_pipeline.py` | `_live_profile_names(conn)` | `for cfg in config.LIVE_STRATEGY_CONFIGS if not ledger.is_strategy_retired(conn, cfg.profile_name)` |

can be a pure `(conn) -> tuple[LiveStrategyConfig, ...]` / `(conn) -> dict[str, LiveStrategyConfig]`
drop-in replacement at every one of them — **zero signature changes** to
`evaluate_kill_conditions`, `_live_profile_names`, `run_entry_pipeline_once`, or
`compute_paper_section` are required beyond swapping the data source.

`trader/paper/config.py`'s own module docstring states: *"This module holds only

minimizes cross-package imports for the four Phase 5 files that already live in

### Recommended schema (`migrations/0006_tournament.sql`)

```sql
-- strategy_registry: the DB-backed replacement for config.py's frozen tuple.
-- Numeric/exit-profile columns are written ONCE at INSERT and never UPDATEd --
-- a changed config is a NEW entrant (D-04), i.e. a new row with a new
-- profile_name, never a mutation of an existing row's frozen columns. `state`
-- is the one column allowed to change, and only via the transitions below.
CREATE TABLE IF NOT EXISTS strategy_registry (
    profile_name TEXT PRIMARY KEY,          -- same identity as today's LIVE_STRATEGY_CONFIGS_BY_PROFILE_NAME keys
    strategy_id TEXT NOT NULL,              -- family name, e.g. "momentum_stock"
    stop_pct REAL,
    tp_pct REAL,
    scale_out_json TEXT NOT NULL DEFAULT '[]',
    trailing_pct REAL,
    max_hold_days INTEGER,
    eod_flat INTEGER NOT NULL DEFAULT 0,
    pf_floor REAL NOT NULL,
    max_dd_kill REAL NOT NULL,
    consecutive_loss_kill INTEGER NOT NULL,
    -- D-07 evidence stamps -- each NULL until that pipeline stage passes.
    backtest_run_id INTEGER REFERENCES backtest_runs(run_id),
    oos_result_ref TEXT,
    paper_30_confirmed_at TEXT,
    entered_at TEXT NOT NULL DEFAULT (datetime('now')),
    state TEXT NOT NULL DEFAULT 'probation' CHECK (state IN ('probation', 'full', 'retired')),
    state_changed_at TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE INDEX IF NOT EXISTS idx_strategy_registry_state ON strategy_registry(state);

-- Append-only transition log, mirroring breaker_events/reconciliation_log's
-- "derive state from history, never trust a bare column alone" convention.
CREATE TABLE IF NOT EXISTS strategy_registry_transitions (
    transition_id INTEGER PRIMARY KEY AUTOINCREMENT,
    ts TEXT NOT NULL DEFAULT (datetime('now')),
    profile_name TEXT NOT NULL REFERENCES strategy_registry(profile_name),
    from_state TEXT,
    to_state TEXT NOT NULL CHECK (to_state IN ('probation', 'full', 'retired')),
    reason TEXT NOT NULL,
    run_id INTEGER REFERENCES tournament_runs(run_id)
);

CREATE TABLE IF NOT EXISTS tournament_runs (
    run_id INTEGER PRIMARY KEY AUTOINCREMENT,
    ts TEXT NOT NULL DEFAULT (datetime('now')),
    config_hash TEXT NOT NULL,           -- frozen tournament RULES hash (D-06 gate), verified this run
    registry_hash_before TEXT NOT NULL,
    registry_hash_after TEXT NOT NULL,
    inputs_snapshot_json TEXT NOT NULL,
    report_path TEXT
);

CREATE TABLE IF NOT EXISTS tournament_decisions (
    decision_id INTEGER PRIMARY KEY AUTOINCREMENT,
    run_id INTEGER NOT NULL REFERENCES tournament_runs(run_id),
    profile_name TEXT NOT NULL,
    decision TEXT NOT NULL CHECK (decision IN ('promote', 'retire', 'hold', 'enter')),
    prior_state TEXT,
    new_state TEXT,
    sharpe REAL,
    profit_factor REAL,
    trade_count INTEGER,
    rank INTEGER,
    rule_citation TEXT NOT NULL
);
```

`LiveStrategyConfig` (the existing frozen dataclass in `config.py`) gains one field
so callers can branch on it: `state: str`. The loader reconstructs
`LiveStrategyConfig` instances fresh from the DB row on every call (the dataclass
itself stays `frozen=True`; only the *row* underneath it can change between
calls, which is exactly D-08's "frozen numeric kill-triggers still immutable per
config version, state can evolve" requirement).

```python
# trader/paper/config_store.py (new module — DB I/O lives here, not in config.py)
def get_live_configs(conn) -> tuple[LiveStrategyConfig, ...]:
    """Rows with state IN ('probation', 'full') only -- retired rows never
    appear, so callers get the same "only tradeable configs" shape
    LIVE_STRATEGY_CONFIGS used to hardcode."""
    rows = conn.execute(
        "SELECT * FROM strategy_registry WHERE state IN ('probation', 'full') "
        "ORDER BY profile_name"
    ).fetchall()
    return tuple(_row_to_live_config(row) for row in rows)

def get_live_configs_by_profile_name(conn) -> dict[str, LiveStrategyConfig]:
    return {cfg.profile_name: cfg for cfg in get_live_configs(conn)}
```

### The one real *behavioral* diff required: probation sizing (25%)

`entry_pipeline.run_entry_pipeline_once`'s per-position loop currently computes
`dollar_amount` **before** `profile_name`/`cfg` are known:

```python
for position in sized["positions"]:
    dollar_amount = position["weight"] * config.PAPER_ACCOUNT_EQUITY
    price = market_data[...]["bars"][-1]["close"]
    qty = broker_ibkr.round_shares_down(dollar_amount, price)
    if qty <= 0:
        continue
    profile_name = assign_exit_profile(position["symbol"], live_profile_names)
    cfg = config.LIVE_STRATEGY_CONFIGS_BY_PROFILE_NAME[profile_name]
```

To apply D-04's 25% probation-size multiplier, `profile_name`/`cfg` must be
resolved **before** `dollar_amount` is computed, since `dollar_amount` is what
needs scaling. `assign_exit_profile(symbol, live_profile_names)` only needs
`position["symbol"]` and the already-available `live_profile_names` list — both
are available before the `dollar_amount` line today, so this reordering is safe
and does not change the symbol-only hash assignment's behavior. Recommended
concrete edit (3 lines moved, 1 line added):

```python
for position in sized["positions"]:
    profile_name = assign_exit_profile(position["symbol"], live_profile_names)
    cfg = live_configs_by_name[profile_name]
    multiplier = tournament_frozen_config.PROBATION_SIZE_MULTIPLIER if cfg.state == "probation" else 1.0
    dollar_amount = position["weight"] * config.PAPER_ACCOUNT_EQUITY * multiplier
    price = market_data[...]["bars"][-1]["close"]
    qty = broker_ibkr.round_shares_down(dollar_amount, price)
    if qty <= 0:
        continue
```

The STEP 0 / STEP 1 heal paths (`_run_step0_heal_pass`, the per-candidate heal
check) must **not** apply this multiplier — they reconstruct an already-decided
`qty` from a prior order, and resizing a healed fill retroactively would silently
misrepresent what was actually filled at the broker. Only the STEP 4/5 new-order
path needs the multiplier.

### Pitfall found: `strategy_kill_state.reason` CHECK constraint blocks tournament retirement

`migrations/0005_paper_trading.sql` defines:

```sql
reason TEXT NOT NULL CHECK (reason IN (
    'profit_factor_floor', 'max_drawdown', 'consecutive_losses'
))
```

D-08 requires "Retire also triggers the existing kill/retire path" — i.e. the
tournament's demotion/kill decision should call `ledger.retire_strategy(conn,
profile_name, reason, trigger_value)`. **Calling it with `reason='tournament_demotion'`
today would raise a `sqlite3.IntegrityError`** because that value is not in the
CHECK list. SQLite cannot `ALTER TABLE ... ADD CONSTRAINT`; migration `0006` must
recreate `strategy_kill_state` (create-new, copy rows, drop old, rename) with an
expanded CHECK including at minimum `'tournament_demotion'`. Flag this explicitly
in the plan — it is an easy thing to miss until the first real retire call
crashes.

### Recommendation on redundant retirement checks

`entry_pipeline._live_profile_names` currently double-checks
`ledger.is_strategy_retired(conn, cfg.profile_name)` against `strategy_kill_state`.
Once `config_store.get_live_configs` already filters by `strategy_registry.state`,
this check becomes redundant but harmless (defense in depth — both systems must
agree a config is live). Recommend **keeping it** rather than removing it: it costs
nothing and preserves the existing "if the system and any internal state
disagree, prefer the more conservative answer" pattern the codebase uses
elsewhere (standing rule 4's spirit).

## Q2: Sharpe on Closed-Trade Returns — Annualisation Convention

**Confidence: HIGH** — `[VERIFIED: codebase]`, `trader/backtest/metrics.py` read directly.

`metrics.py` already computes Sharpe from a **daily-marked equity curve**, not raw
per-trade returns: `compute_metrics` builds `_build_daily_equity_curve` (groups
trades by `exit_ts` date, sums pnl per date, 0-fills no-trade days, cumulates from
a `starting_equity` constant), then feeds the day-over-day % changes into
`sharpe_ratio`, which annualises via `* sqrt(252)` with sample stdev (`ddof=1`).

**Recommendation: reuse `compute_metrics` unchanged, per strategy.** Judging Sharpe
for a `profile_name` = `metrics.compute_metrics(ledger.get_recent_trades(conn,
profile_name, limit=30))["sharpe_ratio"]`, using the same `starting_equity`
constant everywhere (`config.PAPER_ACCOUNT_EQUITY`, 100,000) so every strategy's
daily returns are computed against the identical fixed notional base. This
directly satisfies the canonical reference's "reuse metrics.py, never reimplement"
instruction (`.planning/phases/03-strategy-lab/KILL-CONDITIONS.md` and the D-08
canonical refs list both cite this module) — **zero new statistics code is
required for judging.**

**Why the fixed base matters:** Sharpe on a daily-return series is *not* scale-
invariant to the choice of starting-equity denominator, because trade `pnl`
values are fixed real dollars from the ledger, not dollars that scale with a
chosen notional. Two strategies judged against different `starting_equity` values
would not be comparable. Reusing the single existing `PAPER_ACCOUNT_EQUITY`
constant for every strategy's judging calculation keeps all Sharpe numbers in the
system on the same footing (backtest Sharpe, account-level breaker Sharpe, and now
tournament judging Sharpe).

**Comparability pitfall (flag explicitly):** the daily-equity/√252 convention
0-fills every day a strategy has no closed trade. A low-frequency, high-conviction
strategy's daily-return series is mostly zeros with occasional spikes, which
tends to *understate* variance relative to a higher-frequency strategy with the
same overall profit factor — biasing Sharpe comparisons across strategies with
very different hold times or trade frequency. D-03's tie-break on profit factor
partially compensates for this, but it does not fully correct it. Document this
limitation directly in the frozen tournament config file's docstring (mirroring
`config.py`'s own PAPER_ACCOUNT_EQUITY assumption note) so a future reader
understands why PF is a tie-break rather than pure noise-reduction.

## Q3: Pre-Registered Demotion Rule — Concrete Formula

**Confidence: MEDIUM** — the *shape* (rolling window + consecutive-evaluation
sustain + rank-and-floor compound condition) is `[VERIFIED: codebase pattern]`
(mirrors `guardian.evaluate_kill_conditions`'s existing rolling-30-trade window
convention exactly). The specific numeric defaults below are `[ASSUMED]` —
reasonable, but the owner should confirm them before they are frozen per D-06,
since multiple defensible choices exist.

**Recommended formula:**

> A `full`-state strategy is demoted to `retired` when, for **K=4 consecutive
> weekly tournament evaluations**, it is BOTH (a) ranked worst among all `full`-
> state strategies by judging Sharpe, AND (b) its rolling-30-trade judging Sharpe
> is below `SHARPE_DEMOTION_FLOOR`.

Rationale for the compound condition (rank alone is rejected): rank-alone always
demotes *someone* even in a healthy cohort where every strategy is performing
well — a relative-only rule would eventually empty the roster through attrition
even with a set of genuinely good strategies. Requiring the floor condition too
means "worst of a good bunch" is never demoted, only "worst of a bad bunch, and
genuinely bad."

**Recommended numeric defaults (confirm before freezing):**

| Constant | Recommended value | Rationale |
|---|---|---|
| `JUDGING_WINDOW_TRADES` | 30 | Matches D-03's eligibility minimum and `guardian.evaluate_kill_conditions`'s existing rolling-30 kill-condition window — one consistent "recency window" concept across the whole codebase |
| `SHARPE_PROMOTION_FLOOR` (probation → full) | 0.0 | Net risk-adjusted-positive over the window; a strategy that hasn't cleared this after 30 probation trades has not demonstrated an edge worth full size |
| `SHARPE_DEMOTION_FLOOR` (full → retired, sustained) | 0.0 | Symmetric with the promotion floor — falling back below the bar that earned promotion, sustained, is grounds for demotion |
| `DEMOTION_SUSTAIN_EVALUATIONS` (K) | 4 | One calendar month of weekly evaluations — long enough to filter noise, short enough not to let a genuinely failing strategy run for a quarter |

`pf_floor` (0.9, already used by the D-01 kill conditions) stays the tie-break per
D-03, unchanged from its current role — the tournament introduces no new PF
threshold.

## Q4: Audit Record Design

**Confidence: HIGH** — pattern `[VERIFIED: codebase]` against `breakers.py`'s
append-only-event-log-plus-derived-view convention and `metrics.write_report`'s
markdown-report-per-run convention.

Two distinct "hash" concepts are both needed for D-09's "config hash before/after"
requirement, and conflating them is a likely planning mistake:

1. **Tournament rules hash** (D-06 freeze gate) — a `frozen_config_v2.py`-style
   sha256 over the tournament's own threshold-defining file(s)
   (`trader/tournament/frozen_config.py`). This is *verified*, not recorded as a
   before/after pair — the run aborts via `RuntimeError` if it doesn't match, the
   same way `verify_frozen_v2()` does today. Recorded once per run in
   `tournament_runs.config_hash` as evidence the gate passed.
2. **Registry state hash** (D-09's actual "before/after") — a hash of the
   `strategy_registry` table's `(profile_name, state)` pairs, computed once before
   any decision in a run is applied and once after all decisions are applied.
   This is what lets a human audit glance at `tournament_runs.registry_hash_before`
   vs `registry_hash_after` and know at a glance whether anything changed, without
   diffing the full `inputs_snapshot_json`.

`tournament_decisions` rows must each carry a `rule_citation` string (e.g. `"D-04
promotion: sharpe=0.34 >= 0.0 floor @ 30 trades"`) — this is the literal mechanism
that satisfies "Owner audit is the phase's exit check — decisions must be
traceable to numbers" (D-09/CONTEXT.md `<specifics>`). A decision row without a
citation string fails the phase's own exit gate in spirit even if the numbers are
technically present elsewhere.

Rendered markdown report path convention: mirror `metrics.write_report`'s
`{base_dir}/{YYYY-MM-DD}-{...}.md` pattern — recommend
`reports/tournament/{YYYY-MM-DD}-run{run_id}.md`, matching the existing
`reports/backtests/` sibling directory's naming.

## Q5: Static HTML Dashboard Without New Dependencies

**Confidence: HIGH** — `[VERIFIED: pip list against the actual project venv]`. Only
`numpy 2.5.1`, `pandas 3.0.5`, and `pandas_market_calendars 5.4.0` are installed;
**no matplotlib, no plotly, no any charting library.**

**Recommendation:** hand-roll inline SVG polylines — no new dependency, no
subprocess, no headless-browser rendering. A small pure-Python helper
(`trader/tournament/svg_chart.py`) that takes a list of equity-curve floats and
emits a `<svg viewBox="0 0 W H"><polyline points="x1,y1 x2,y2 ..." .../></svg>`
string, scaling x by index and y by `(value - min) / (max - min)`. This is
trivially testable (assert the emitted string contains the right number of
comma-pairs and stays within the viewBox bounds) and embeds directly into the
single self-contained HTML file D-01 requires — no `<script>` tag, no external
asset, satisfies "no server, no JS frameworks" exactly.

Do not add matplotlib to solve this — it would be the first plotting dependency
in the entire project, adds a large binary dependency (and on Windows, a
non-trivial wheel) for a problem inline SVG solves in ~20 lines of stdlib string
formatting.

## Common Pitfalls

### Pitfall 1: DB I/O leaking into `trader/paper/config.py`
**What goes wrong:** A tempting minimal-diff shortcut is to add a DB read
directly inside `config.py` next to the existing `LIVE_STRATEGY_CONFIGS` tuple.
**Why it happens:** `config.py` is the file every consumer already imports as
`config`, so adding a function there feels like the smallest diff.
**How to avoid:** Put the loader in a new module (`config_store.py`); `config.py`'s
own docstring promises "no engine logic, no I/O" and downstream trust in that
contract (e.g. it being safe to import at module scope with no side effects)
should not be broken silently.
**Warning signs:** A `sqlite3` or `trader.data.db` import appearing in
`trader/paper/config.py`'s diff.

### Pitfall 2: `strategy_kill_state.reason` CHECK constraint rejects tournament retirements
**What goes wrong:** Calling `ledger.retire_strategy(conn, profile_name,
"tournament_demotion", value)` raises `sqlite3.IntegrityError` because
`'tournament_demotion'` is not in the existing three-value CHECK list.
**Why it happens:** The constraint was written for D-01's five hardcoded
kill-condition reasons only, before a tournament-driven retirement existed.
**How to avoid:** Migration `0006` must recreate `strategy_kill_state` with an
expanded CHECK. Test this explicitly — a fixture that calls `retire_strategy`
with a tournament-shaped reason and asserts it does not raise.
**Warning signs:** Any tournament retire-path test that only checks
`strategy_registry.state` and never actually calls `ledger.retire_strategy` end
to end would hide this bug.

### Pitfall 3: Applying the probation-size multiplier in the wrong loop
**What goes wrong:** Applying `PROBATION_SIZE_MULTIPLIER` inside the STEP 0 / STEP
1 heal paths (which reconstruct a position from an *already-placed* order) instead
of only the STEP 4/5 new-order path.
**Why it happens:** All three paths call `ledger.open_position`, making it look
like "the" place sizing happens — but only STEP 4/5 actually computes a fresh
`qty` from `weight`.
**How to avoid:** Multiplier only touches the `dollar_amount` computation in the
new-order branch; heal paths reuse `local_order["qty"]` verbatim, exactly as they
do today.
**Warning signs:** A healed fill's `qty` in `paper_positions` not matching the
`qty` on the original `paper_orders` row.

### Pitfall 4: Comparing Sharpe across strategies with different `starting_equity` bases
**What goes wrong:** Computing each strategy's daily-equity curve against a
per-strategy notional (e.g. its own allocated capital) rather than one fixed
constant for every strategy, silently making Sharpe values non-comparable for
ranking purposes.
**How to avoid:** Always call `metrics.compute_metrics(trades, starting_equity=config.PAPER_ACCOUNT_EQUITY)`
with the same constant for every strategy being judged in a given run.
**Warning signs:** Ranking output that looks suspiciously correlated with
position size rather than risk-adjusted skill.

### Pitfall 5: Rank-only demotion emptying a healthy roster
**What goes wrong:** A demotion rule based on relative rank alone (no absolute
floor) will always demote the worst-ranked `full` strategy every K evaluations,
even when every active strategy is profitable — eventually reducing the roster to
zero or one strategy through pure attrition.
**How to avoid:** The compound condition in Q3 (rank AND below-floor,
sustained) — never rank alone.
**Warning signs:** A backtest of the tournament rule against synthetic
all-profitable fixtures still producing retirements.

### Frozen-config hash gate, mirroring `frozen_config_v2.py` exactly
```python
# Source: trader/backtest/frozen_config_v2.py (structural pattern, verified this session)
import hashlib
from pathlib import Path

FROZEN_FILES: tuple[str, ...] = ("trader/tournament/frozen_config.py",)

def compute_hash(repo_root: Path | None = None) -> str:
    if repo_root is None:
        repo_root = Path(__file__).resolve().parents[2]
    digest = hashlib.sha256()
    for rel_path in FROZEN_FILES:
        digest.update((repo_root / rel_path).read_bytes())
    return digest.hexdigest()

FROZEN_HASH = "<computed once, committed literal>"

def verify_frozen(repo_root: Path | None = None) -> None:
    actual = compute_hash(repo_root)
    if actual != FROZEN_HASH:
        raise RuntimeError("tournament frozen config integrity check failed ...")
```

### Minimal inline-SVG equity curve (no dependency)
```python
# trader/tournament/svg_chart.py -- pure stdlib, no matplotlib available (verified: pip list)
def equity_curve_svg(values: list[float], width: int = 400, height: int = 100) -> str:
    if len(values) < 2:
        return "<svg></svg>"
    lo, hi = min(values), max(values)
    span = (hi - lo) or 1.0
    step = width / (len(values) - 1)
    points = " ".join(
        f"{i * step:.1f},{height - ((v - lo) / span) * height:.1f}"
        for i, v in enumerate(values)
    )
    return (
        f'<svg viewBox="0 0 {width} {height}" xmlns="http://www.w3.org/2000/svg">'
        f'<polyline points="{points}" fill="none" stroke="black" stroke-width="1.5"/></svg>'
    )
```
