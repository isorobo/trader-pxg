<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| trader/data/classify.py → api.coingecko.com | outbound HTTPS call carrying the CoinGecko demo API key |
| api.coingecko.com response → classify_crypto_instrument | untrusted third-party JSON parsed before use |
| register_crypto_instrument → trader/data/db.py | persists a classification result via the already-parameterized upsert_instrument helper |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-04 | Tampering | classify.py response parsing | mitigate | `categories = response.json().get("categories") or []` defends against a missing/malformed key; `raise_for_status()` guards non-200 responses before any parsing |
| T-01-05 | Denial of Service | CoinGecko rate limiting | mitigate | classify_crypto_instrument requires an api_key argument and always sends the x-cg-demo-api-key header; register_crypto_instrument only calls it once per new instrument (never per bar fetch), avoiding the empirically-confirmed sub-10-call unauthenticated 429 (01-RESEARCH.md Pitfall 3) |
| T-01-06 | Information Disclosure | api_key handling | mitigate | api_key is never written to a log line or exception message; only coingecko_id and HTTP status appear in any log output |
| T-01-14 | Tampering | register_crypto_instrument persistence | accept (delegated) | register_crypto_instrument never builds SQL itself; it delegates persistence entirely to trader/data/db.py's already-parameterized upsert_instrument (T-01-01 from Plan 01-01) |
</threat_model>
